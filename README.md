# law_AI_FE

> **법안잇다** — 흩어진 법안의 조각, 한눈에 잇다.
> **유사 법률안 검색 · 비교 · 요약 서비스**의 프론트엔드입니다.
> 열린국회정보(22대 발의법률안) 데이터를 서버(BE)가 가공해서 내려주면, 이 앱이 검색 화면과 비교 화면으로 보여줍니다.

- 서버(BE) 레포: _(링크 추가)_
- 데이터 출처: 열린국회정보 Open API (발의법률안 목록, 법률안 제안이유 및 주요내용)
- AI 분석(유사도, 요약, 비교)은 **서버에서** 수행하고, 이 앱은 결과를 보여주는 역할만 합니다.

---

## 1. 서비스 소개

국회에는 같은 법을 고치거나 비슷한 내용을 담은 법률안이 매우 많습니다. 제목만 봐서는 무엇이 다른지 알기 어렵습니다.
이 서비스는 **일상적인 키워드로 관련 법률안을 찾고, AI 요약으로 내용을 빠르게 파악하고, 두 법률안을 골라 차이점을 비교**할 수 있게 합니다.

> 예) 사용자가 `월세 지원금`을 검색 → 관련 법률안이 관련도 순으로 나열 → 궁금한 법률안만 `AI 요약 확인하기`로 요약 확인 → 마음에 드는 두 법률안을 선택 → 주제별 차이점 확인

## 2. 핵심 기능

### 2-1. 키워드 검색

| 항목 | 내용 |
|---|---|
| 입력 | 자연스러운 키워드 한 줄 (예: `월세 지원금`, `전세사기`, `청년 교통혜택`) |
| 동작 | 검색어를 서버에 전달하고, 결과를 받아 목록으로 표시 |
| 보조 기능 | 예시 검색어 칩(클릭하면 바로 검색), 최근 검색어(선택 사항) |
| 상태 처리 | 로딩 / 결과 없음 / 오류 / 빈 입력 |

- 검색 방식(키워드 매칭, 유의어 확장 등)은 서버가 정합니다. 프론트는 검색어를 가공하지 않고 그대로 보냅니다.
- 법률안 이름이나 본문에 해당 단어가 없으면 검색되지 않을 수 있습니다. 결과가 적으면 "다른 키워드로 검색해 보세요" 안내를 보여줍니다.

### 2-2. 검색 결과 목록 (관련도 순 + AI 요약 버튼)

- 기본은 서버가 준 **관련도(score) 순서 그대로** 보여줍니다.
- 정렬 메뉴에서 `처리 단계순`을 고르면 심사 중 → 본회의 통과 → 대안에 반영(폐기) → 기타 → 처리 결과 미제공 순으로 묶습니다. 같은 단계 안에서는 관련도 순서를 유지합니다.
- 처리 단계순일 때 단계 박스(심사 중 · 본회의 통과 · 대안에 반영(폐기) · 기타 · 처리 결과 미제공, 각 건수 표시)가 나옵니다. 누른 단계의 법안만 보여주고, 여러 개를 함께 고를 수 있습니다. 아무것도 고르지 않으면 전체를 보여주고, 해당 단계가 0건이면 박스를 누를 수 없습니다. 관련도순으로 돌아가면 선택이 풀립니다.
- 정렬 메뉴 옆의 `소관위` 필터에서 17개 위원회 중 하나를 고릅니다. 관련도순·처리 단계순 모두에서 쓸 수 있으며, 선택한 처리 단계와 함께 적용됩니다. 필터를 바꾸면 1페이지로 돌아가고, 결과가 없으면 필터 초기화를 안내합니다. 필터와 건수는 이번에 받은 검색 결과(최대 100건)에만 적용됩니다.
- 소관위 목록: 국회운영위원회, 법제사법위원회, 정무위원회, 재정경제기획위원회, 교육위원회, 과학기술정보방송통신위원회, 외교통일위원회, 국방위원회, 행정안전위원회, 문화체육관광위원회, 농림축산식품해양수산위원회, 산업통상자원중소벤처기업위원회, 보건복지위원회, 기후에너지환경노동위원회, 국토교통위원회, 정보위원회, 성평등가족위원회. 그 밖의 이름이 실제 응답에 있으면 그대로 추가하며 다른 위원회로 임의 변환하지 않습니다. 필터별 건수는 단계 필터 적용 전 전체 검색 결과 기준입니다.
- 소관위 정보가 없는 법안은 `소관위 정보 없음`으로 구분합니다. 현재 배포 검색 API에는 소관위가 없으므로 실제 위원회별 분류에는 BE의 `COMMITTEE` 필드 추가가 필요합니다.
- 법안 제목과 카드의 `제안이유 및 주요내용`(원문) 안에서 검색어와 같은 부분에 노란 형광펜을 칠합니다. 제목은 원문 링크 유무와 관계없이 표시하고, 검색어를 띄어쓰기로 나눈 단어마다 칠합니다. 접힌 원문 옆의 `검색어 N곳`은 원문 안의 일치 횟수입니다. 서버에 보내는 검색어는 그대로입니다.
- 카드의 요약 자리에는 처음에 `AI 요약 확인하기` 버튼만 왼쪽에 둡니다. 요약이 나오면 `AI 요약` 이름표와 함께 보여줍니다.
- 법률안 카드 한 장에 들어가는 정보

| 표시 항목 | 설명 |
|---|---|
| 법안명 | 원문 URL이 있으면 새 탭 링크, 없으면 링크 미제공 안내 |
| 의안번호 · 소관위 · 발의자 · 발의일 | 메타 정보 (소관위는 검색 응답, 발의자·발의일은 8-9 상세 정보) |
| 처리 상태 뱃지 | 본회의 통과 / 대안에 반영(폐기) / 심사 중 (아래 [상태 표시 규칙](#5-ui-규칙) 참고) |
| 매칭된 키워드 | 현재 API 미제공으로 숨김 |
| **AI 요약 확인하기** | 버튼을 누른 법안만 서버에 요약을 요청해 카드 안에 보여줌 |
| 비교에 담기 | 체크하면 비교 바구니에 추가 (최대 2건) |

- **AI 요약은 미리 만들지 않습니다.** 검색 결과마다 요약을 만들면 AI 토큰이 낭비되므로, 사용자가 `AI 요약 확인하기`를 누른 법안만 요약을 요청합니다([8-2](#8-2-법안-요약-버튼을-눌렀을-때만)).
- 한 번 받은 요약은 다시 요청하지 않습니다. 다른 화면에 다녀와도 그대로 보입니다(새로고침 전까지).
- 요약을 만드는 동안 버튼에 "요약하는 중…"을 표시합니다.
- AI 요약이 없으면(`summary: null`, 원문 없음 등) "요약을 준비하지 못했어요. 원문 링크를 확인하세요"를 표시합니다.
- 요청 자체가 실패하면 "요약을 불러오지 못했어요"와 `다시 시도` 버튼을 표시합니다.
- 요약 아래에 "AI가 생성한 요약이며 원문과 다를 수 있습니다." 안내를 표시합니다.
- 현재 비교 API는 개별 요약을 포함하지 않아, 비교 화면에서도 버튼을 누른 법안만 요약합니다.

### 2-3. 두 법률안 비교

1. 검색 결과에서 법률안 **2건**을 선택하면 화면 아래에 비교 바(`비교할 법안 2/2 · 비교하기`)가 나타납니다.
2. `비교하기`를 누르면 비교 화면(`/compare`)으로 이동합니다.
3. 비교 화면 구성

| 영역 | 내용 |
|---|---|
| 상단 | 법률안 A, B의 이름 · 소관위 · 상태 · 원문 링크 · 각각의 AI 요약 |
| 비슷한 내용 | 현재 API 미제공으로 숨김 |
| **차이점** | 같은 주제의 A/B 내용을 행마다 나란히 표시 |
| **AI 비교 요약** | 현재 API 미제공으로 숨김 |

- 비교 바구니는 다시 검색해도 비워지지 않습니다. **서로 다른 키워드로 찾은 법안끼리도** 비교할 수 있습니다.
- 비교 화면 주소는 `/compare?a=<의안번호>&b=<의안번호>` 형태로 만들어서, **링크만 공유해도 같은 비교 결과**를 볼 수 있게 합니다.
- 비교 결과는 생성에 시간이 걸릴 수 있으니 로딩 상태(스켈레톤)를 보여줍니다.

### 2-4. 법안 저장

- 법률안 카드의 `저장` 버튼으로 법안을 저장하고, 사이드바 `저장한 법안`(`/saved`)에서 모아 봅니다.
- 저장한 법안 화면에서도 2건을 골라 비교할 수 있습니다.
- 로그인 기능이 없으므로 **브라우저(localStorage)에만** 보관합니다. 다른 기기·브라우저와 공유되지 않습니다. 서버 저장이 필요해지면 BE와 API를 협의합니다.

## 3. 화면 구성

- `/`: 검색 전 기능 소개, 검색 후 실제 검색 결과(최대 100건, 한 페이지 20건씩 최대 5페이지, 아래 번호로 이동), 법안 카드의 원문 내용 접기·AI 요약 버튼·`이 법안이 적용되면?` 맞춤 요약·저장·비교 선택. 숫자 7자리 검색은 의안번호로 찾는다.
- `/saved`: 이 브라우저에 저장한 법안 목록과 비교 선택.
- `/compare?a=...&b=...`: A/B 법안 카드와 선택적 AI 요약, 같은 주제의 차이점을 행별로 나란히 표시.
- 검색·비교 요청은 로딩·오류·재시도를 처리한다. 검색은 준비 중과 결과 없음을 구분한다. 검색해도 비교 바구니는 비워지지 않는다.

## 5. UI 규칙

### 상태 표시 규칙

법안의 처리결과 `PROC_RESULT`를 API 계층에서 아래 UI 상태로 변환합니다(8-1 참고).

| `status` | 화면 표기 | 의미 |
|---|---|---|
| `PASSED` | 본회의 통과 | 본회의에서 원안가결 또는 수정가결된 법안. 시행 시기는 별도이므로 원문 링크에서 확인 |
| `MERGED` | 대안에 반영(폐기) | 위원회 대안에 내용이 흡수되고 이 법안은 폐기됨. **통과가 아님**. 대안의 처리 여부는 원문 링크에서 확인 |
| `REVIEW` | 심사 중 | 국회에서 심사 중이며 통과 여부 미정 |
| `OTHER` | 기타 | 그 외 처리결과 (철회 등) |

> `MERGED`를 "통과"로 표시하면 사용자가 오해하므로 **절대 같은 색·같은 문구로 표시하지 않습니다.**

### 필수 고지 문구

- 모든 AI 요약/비교 영역: **"AI가 생성한 요약이며 원문과 다를 수 있습니다."**
- 푸터(비교 화면 포함 모든 화면 하단): **"법률 자문이 아닌 정보 안내입니다. 정확한 내용은 원문을 확인하세요."** 비교 화면 본문에는 중복해서 두지 않습니다.
- 예외: 맞춤 요약(8-7) 결과 하단은 위 두 문구를 한 줄로 줄여 **"AI 요약은 원문과 다를 수 있으며, 법률 자문이 아닙니다. 정확한 내용은 원문을 확인하세요."**로 표시합니다.
- 법률안 카드의 제목을 누르면 국회 의안정보시스템의 **원문 페이지**가 새 탭으로 열립니다(8-9). 링크가 없거나 불러오지 못하면 그 사실을 안내하고 접힌 원문 내용을 표시합니다.

### 공통

- 모바일 화면(폭 360px 이상)에서 깨지지 않게 만듭니다.
- 버튼, 입력창은 키보드로 조작할 수 있어야 합니다.

## 6. 시작하기

### 준비물

- Node.js (LTS), npm
- Git

### 설치 및 실행

```bash
git clone <이 레포 주소>
cd law_AI_FE
npm install
npm run dev
```

브라우저에서 `http://localhost:5173`이 열리면 성공입니다.

### 실제 서버로 화면 확인하기

`npm run dev` 후 표시되는 로컬 주소를 연다. `소방` 등의 키워드로 검색하고 카드의 `AI 요약 확인하기`, 저장, 법안 2건 비교를 확인한다. 다시 검색해도 비교 바구니는 유지된다. 비교 주소를 새 탭에서 열어도 의안번호로 비교 요청이 가능하다.

수집 전에는 데이터 준비 중 안내가 표시된다. 결과가 없거나 요청이 실패하면 각각 별도 안내를 표시한다. 실제 실행 화면에서는 mock을 사용하지 않는다. `src/api/mock.js`는 테스트용 응답 예시다.

### 자주 쓰는 명령

실제 스크립트 목록은 `package.json`의 `scripts`를 확인하세요.

| 명령 | 설명 |
|---|---|
| `npm run dev` | 개발 서버 실행 |
| `npm run build` | 배포용 빌드 (PR 전에 실행해서 오류가 없는지 확인) |
| `npm run lint` | 코드 검사 (PR 전에 실행) |
| `npm test` | API 요청·변환·캐시·오류 처리 테스트 |

### 환경 변수

- 환경 변수는 `.env`에 두고 **절대 커밋하지 않습니다.** (`.gitignore`에 포함)
- **Vite에서 `VITE_`로 시작하는 변수는 브라우저에 그대로 노출됩니다.** 인증키·API 키는 프론트에 두지 않고 **서버에서만** 사용합니다.

- `docs/`의 PDF·Word는 11월 11일 당시 논의 기록이다. 현재 연동은 배포 서버의 OpenAPI를 기준으로 한다.

개발 서버와 `npm run preview`에서는 브라우저가 `/api/...`로 요청하면 Vite가 `/api` 접두사를 제거해 Railway로 전달한다. 예: `/api/search?query=소방` → BE `/search?query=소방`.

설정 없이 `npm run dev`로 실제 서버와 연결된다. 로컬 BE를 사용하려면 `.env.local`에 `API_PROXY_TARGET=http://localhost:8000`을 설정하고 개발 서버를 다시 시작한다. 키·토큰은 FE 환경 변수에 넣지 않는다.

정적 배포에서는 Vite 프록시가 실행되지 않는다. 호스팅에서 `/api/*`를 BE `/*`로 프록시하거나, `VITE_API_BASE_URL=https://law-ai-be-production.up.railway.app`로 빌드하고 BE에서 FE 배포 주소의 CORS를 허용해야 한다. 11월 18일 localhost Origin으로 받은 검색 응답에는 CORS 허용 헤더가 없어 직접 호출하는 정적 배포는 BE 설정 확인이 필요하다.

데이터 수집은 BE 서버가 켜질 때 자동으로 시작한다(`/preprocess` API는 삭제됨). 준비가 끝나기 전 검색은 `preprocess: false`로 응답하고, 화면은 준비 중으로 안내한다.

## 8. API 명세 (배포 서버 기준)

### 8-1. 검색

`GET /search?query={검색어}&limit=100` (limit: 1~100, FE는 최대값 100으로 한 번에 받음)

`COMMITTEE`(소관 상임위원회)는 문자열 또는 null이고, `SUMMARY`도 원문이 아직 등록되지 않았으면 null일 수 있습니다. `COMMITTEE`가 없는 예전 응답도 지원합니다.

검색어가 숫자 7자리면 의안번호로 보고 8-8 조회를 먼저 사용합니다. 해당 법안이 없으면(404) 같은 검색어를 그대로 `/search`로 보냅니다.

```json
{
  "preprocess": true,
  "data": [{
    "BILL_NO": "0000001",
    "BILL_NAME": "예시 법률안 A",
    "COMMITTEE": "국토교통위원회",
    "PROC_RESULT": null,
    "SUMMARY": "국회 원문인 제안이유 및 주요내용 (AI 요약 아님)",
    "SCORE": 0.4916
  }]
}
```

- `SCORE`는 0~1 사이 소수인 관련도다(11월 18일 BE 변경: 키워드 점수 50% + Word2Vec 의미 점수 50%). 카드에 `관련도 49%`처럼 반올림한 백분율로 표시한다. 0~1 범위를 벗어나거나 숫자가 아니면 잘못된 응답으로 처리한다.
- 검색어를 그대로 전달하고 응답 순서를 유지한다. FE의 소문자 카드 필드로 변환하는 작업만 `src/api/bills.js`에서 수행한다.
- `preprocess: false`는 데이터 준비 중, `true`와 `data: []`는 검색 결과 없음으로 구분한다. HTTP 503 + `NOT_READY`도 준비 중으로 처리한다.
- `SUMMARY`를 AI 요약으로 표시하지 않는다. 카드의 접힌 `제안이유 및 주요내용`에서 원문으로 표시한다. null이면 원문 미등록을 안내하고 AI 버튼을 숨긴다(BE가 404를 주기 때문).
- `PROC_RESULT`: 원안가결·수정가결 → PASSED, 대안반영폐기·수정안반영폐기 → MERGED, null·빈 문자열 → REVIEW, 그 밖의 값 → OTHER. 상세 정보가 아예 없는 공유 링크의 법안은 UNKNOWN(처리 결과 미제공)으로 구분한다. 상태 변환은 기존 연동 논의 기준이며 BE와 최종 확인이 필요하다.
- 선택 필드 `COMMITTEE`가 문자열이면 앞뒤 공백만 제거해 `committee`에 보관합니다. 누락·null·빈 문자열은 null로 처리하고, 다른 타입은 잘못된 응답으로 처리합니다. 법안 제목이나 본문에서 소관위를 추측하지 않습니다.
- 검색 응답에 발의일·원문 URL·매칭 키워드는 없다. 발의자·발의일·원문 링크는 8-9로 받고, `BILL_ID`로 링크를 직접 만들지 않는다. 소관위가 null인 법안은 `소관위 정보 없음` 필터로 구분한다.
- BE는 핵심어 포함 비율 → 법률안 형식 → `SCORE` → 최신순으로 정렬한다. 그래서 관련도 %가 내림차순이 아닐 수 있고, FE는 서버 순서를 그대로 유지한다.
- `total`이 없으므로 화면의 건수는 이번에 받은 결과 수(최대 100건)다. 100건이 넘는 결과는 BE에 페이지(offset) 기능이 없어 받을 수 없다.
- FE는 받은 결과를 순서 그대로 20건씩 나눠 보여준다(최대 5페이지). 페이지를 넘겨도 다시 요청하지 않는다.

### 8-2. 법안 AI 요약

`GET /summary?bill_no={의안번호}`

```json
{ "bill_no": "0000001", "summary": "AI가 쉽게 풀어 쓴 요약" }
```

카드에서 `AI 요약 확인하기`를 누른 경우만 요청한다. 성공 응답과 진행 중 요청은 의안번호별로 공유해 중복 요청을 막고, 실패는 캐시하지 않아 재시도할 수 있다. 비교 화면에서도 같은 버튼·캐시를 사용한다. 404(법안/원문 없음), 502(AI 실패), 422(입력 오류)를 처리한다. 방어적으로 `summary: null`도 허용한다.

### 8-3. 두 법률안 비교

`GET /compare?a_bill_no={A 의안번호}&b_bill_no={B 의안번호}`

```json
{
  "a_bill_no": "0000001",
  "b_bill_no": "0000002",
  "differences": [["비교 항목 소제목", "같은 주제에 관한 A의 내용", "같은 주제에 관한 B의 내용"]]
}
```

- `differences`의 각 원소는 `[소제목, A, B]`다. 소제목이 빈 값이면 `비교 항목`을 표시하고, FE에서 소제목을 만들지 않는다.
- 문장에 `==핵심==`, `**강조**` 표시가 오면 형광 표시와 굵은 글씨로 보여준다. 현재 BE 응답에는 이 표시가 없어 글자 그대로 나온다.
- 화면은 번호 + 소제목 아래에 A | VS | B를 나란히 놓는다. 모바일에서는 A, VS, B를 세로로 쌓고 법안 이름표를 표시한다.

- 원소마다 한 행으로 나란히 표시한다. 법안 순서를 바꾸면 별도 요청으로 취급한다.
- 현재 API는 개별 요약, 법안 이름·상태, 유사도, 공통점, 종합 비교 요약을 함께 주지 않는다. 해당 내용을 만들어 표시하지 않는다. 개별 AI 요약은 8-2 버튼을 사용한다.
- `/compare?a=...&b=...` 주소만으로 비교를 요청할 수 있다. 공유 링크로 들어오면 8-8 조회로 법안 이름·소관위·처리 상태를 채우고, 조회에 실패하면 제목 대신 의안번호를 표시한다.
- 서로 다른 숫자 의안번호 2개만 허용한다. 400·404·422·502 및 네트워크 실패 시 안내와 재시도 버튼을 표시한다. 성공한 동일 A/B 비교는 새로고침 전까지 캐시한다.

### 8-4. 오류 응답

AI 제공자의 내부 오류는 안내 문구로 표시하고 진단 정보는 ApiError.details에 보존한다. FastAPI의 `{ "detail": "설명" }`, 검증 오류의 `{ "detail": [{ "msg": "설명" }] }`, 기존 제안인 `{ "error": { "code": "...", "message": "..." } }`를 공통 클라이언트가 처리한다. 비 JSON 오류·연결 실패·시간 초과도 안내한다. 검색은 30초, AI 요청은 90초 제한을 둔다.

### 8-5. 현재 검증 결과

2026-11-23 배포 서버에서 검색(100건), `/summary`, `/profile`, `POST /happen`, `/search/billno` 성공 응답을 확인했다. 11월 18일의 AI 인증 오류(401)는 해결됐다. 같은 날 BE 변경 후 `/compare`의 `[소제목, A, B]` 응답과 `/info`의 원문 링크·발의자·발의일을 화면에서 확인했다.

### 8-6. BE와 남은 확인 사항

- 검색 응답의 매칭 키워드 추가.
- 비교 기준 고정과 핵심 표현 강조 표시는 BE와 추가 논의.
- PROC_RESULT 상태 변환 규칙 확정, 프론트 배포 주소 CORS 허용(`ALLOWED_ORIGINS`).
- 공통점·유사도·종합 비교 요약은 응답 추가 시 화면 확장.

### 8-7. 맞춤 요약 ("이 법안이 적용되면?")

AI 요약 아래 `이 법안이 적용되면?`을 누르면 조건을 요청하고, 조건을 고른 뒤 `맞춤 요약 보기`를 눌러야 결과를 요청한다. 검색·저장 화면의 카드에서만 제공한다.

`GET /profile?bill_no={의안번호}`

```json
{
  "bill_no": "0000001",
  "targets": ["원문에 나온 대상"],
  "criteria": [{ "name": "기준 이름", "multiple": false, "options": ["선택지 1", "선택지 2"] }]
}
```

`POST /happen`

```json
{
  "bill_no": "0000001",
  "targets": ["원문에 나온 대상"],
  "criteria": [{ "name": "기준 이름", "selected": ["선택지 1"] }]
}
```

응답:

```json
{
  "bill_no": "0000001",
  "applicability": "high",
  "headline": "이 조건에 맞는 분들은 ~할 수 있어요.",
  "changes": [["바뀌는 것", "지금", "법안이 적용되면"]],
  "checks": [{ "condition": "대조한 조건", "status": "match", "reason": "판단 이유" }],
  "evidence": ["원문에서 그대로 인용한 문장"],
  "stage": "심사 중"
}
```

- `applicability`: high(해당될 가능성 높음), medium(확인 필요), low(해당될 가능성 낮음). 응답 검증에는 쓰지만 화면에는 표시하지 않는다(판정은 `headline`과 `checks`로 전달).
- `checks[].status`: match(해당), mismatch(해당 안 됨), unknown(확인 필요). 조건·설명 뒤에 태그로 표시하고, 색만으로 구분하지 않고 글자도 함께 표시한다.
- `evidence`는 카드의 `제안이유 및 주요내용`과 같은 접기(`근거가 된 원문`)로 기본은 접어 둔다.
- 조건 고르기 오른쪽 위 닫기(✕): `조건 변경`으로 열었으면 변경 전 결과로, 처음 열었으면 `이 법안이 적용되면?` 버튼으로 돌아간다.
- 결과 머리말은 `AI 맞춤 요약` 옆에 고른 조건을 유형별 둥근 태그로 묶어 보여준다(같은 유형은 ` · `로 구분).
- `stage`는 AI가 아닌 국회 처리 정보다. `심사 중`은 REVIEW, 나머지는 `PROC_RESULT` 변환 규칙으로 뱃지를 표시한다. 대안반영폐기·철회처럼 법안 그대로 적용되지 않는 경우 그 사실을 함께 안내한다. 이 안내는 결과 맨 아래(고지 문구 위)에 `지금 단계 [뱃지] 설명 (국회 처리 정보)` 한 줄로 보여준다. 원문 링크는 카드 제목에 있으므로 여기에 다시 두지 않는다.
- 조건은 아무것도 고르지 않아도 요청할 수 있다. 빈 기준은 보내지 않는다.
- 같은 법안의 조건 목록과 같은 조건의 결과는 새로고침 전까지 재사용하고, 실패는 저장하지 않아 다시 시도할 수 있다.

### 8-8. 의안번호로 법안 조회

`GET /search/billno?billno={의안번호}`

```json
{
  "preprocess": true,
  "data": { "BILL_NO": "0000001", "BILL_NAME": "예시 법률안 A", "COMMITTEE": null, "PROC_RESULT": null, "SUMMARY": "원문 또는 null" }
}
```

`SCORE`가 없으므로 관련도는 표시하지 않는다. 없는 번호는 404다. 숫자 7자리 검색과 공유 비교 링크의 법안 정보 조회에 사용한다.

### 8-9. 법률안 상세 정보

`GET /info?billno={의안번호}`

```json
{
  "BILL_NO": "0000001",
  "PROPOSER": "예시의원 등 10인",
  "PROPOSE_DT": "2026-01-01",
  "DETAIL_LINK": "https://likms.assembly.go.kr/bill/billDetail.do?billId=..."
}
```

- 응답에는 처리 단계별 날짜 등 다른 필드도 있지만, 카드에는 발의자·발의일·원문 링크만 사용한다.
- 호출마다 BE가 국회 API를 다시 부르므로 **화면에 보이는 카드만** 요청하고, 동시에 최대 3건만 보낸다. 성공한 결과는 새로고침 전까지 재사용한다.
- 링크는 `likms.assembly.go.kr` 주소만 https로 바꿔 사용하고, 다른 주소는 표시하지 않는다.
- 실패해도 카드와 검색은 그대로 쓸 수 있고, 원문 링크를 불러오지 못했다고 안내한다.

```
src/
├─ api/                 서버 호출 함수, mock 데이터

│  ├─ SearchPage.jsx    검색 화면 (/)
│  └─ ComparePage.jsx   비교 화면 (/compare)
├─ components/
│  ├─ SearchBar.jsx     입력창 + 예시 검색어 칩

│  ├─ CompareTray.jsx   하단 비교 바구니

```

## 10. 개발 규칙

### 브랜치와 PR

```bash
git switch main
git pull
git switch -c feature/search-page      # 작업 단위별 브랜치
# 작업 후
git add .
git commit -m "feat: 검색 화면 추가"
```

- 커밋 메시지는 `feat:`(기능), `fix:`(버그), `docs:`(문서), `chore:`(설정·정리), `style:`(화면 스타일)로 시작합니다.
- 브랜치 이름은 `feature/기능이름`, `fix/버그이름` 형식을 씁니다.

## 12. 알아둘 점

- 데이터는 열린국회정보의 **22대 발의법률안**입니다. 발의안일 뿐 통과 여부는 처리 상태를 따릅니다.
- AI 요약과 비교는 서버의 AI가 만든 결과라서 **틀릴 수 있습니다.** 원문 URL은 현재 API 미제공이며 BE 추가 요청 사항입니다.
- 검색은 서버의 검색 방식에 따라 결과가 달라집니다. 검색 품질 문제는 BE 담당과 함께 확인합니다.
